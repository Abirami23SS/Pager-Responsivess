# Skill 10 — Deployment, Hosting & Infrastructure (Mandated)

> **Applies to:** .NET 8 (LTS) · .NET 10 (LTS)
> **Proficiency required:** Intermediate

---

## Summary

Developers must be able to publish, host, and configure Blazor applications correctly across all target environments. The `.NET 8` Blazor Web App unified project model changes the hosting story — a single app can serve Static SSR, WASM, and Interactive Server from one host. Understanding this model is required.

---

## Key Competencies

### Publishing (.NET 8/10)

#### Blazor Web App (unified, .NET 8+)
```bash
# Publish Blazor Web App (Server + optional WASM client project)
dotnet publish -c Release -o ./publish
```
- The unified Blazor Web App project (introduced .NET 8) hosts SSR, Interactive Server, and WASM from a single ASP.NET Core app.
- WASM client project is automatically published as static assets under `_framework/`.

#### Standalone Blazor WASM
```bash
dotnet publish -c Release -o ./publish
# Output: wwwroot/ with _framework/, index.html, Brotli-compressed assets
```
- Deploy `wwwroot/` to any static host (Azure Static Web Apps, GitHub Pages, Nginx, CDN).
- Configure the host to serve `index.html` as fallback for all routes (SPA routing).

### Configuration & Environments
- Use `appsettings.json` + `appsettings.{Environment}.json` hierarchy.
- Inject configuration via `IOptions<T>`, `IOptionsSnapshot<T>`, and `IOptionsMonitor<T>`; never resolve `IConfiguration` directly in components or library code.
- Use environment variables for environment-specific overrides in CI/CD pipelines.
- Use Azure Key Vault provider (or equivalent) for production secrets; configure via `AddAzureKeyVault` in `Program.cs`.

### Hosting Environments

| Environment | Notes |
|---|---|
| **Kestrel** | Default cross-platform host; recommended for containers |
| **IIS / IIS Express** | Requires ASP.NET Core Module; `web.config` auto-generated by publish |
| **Azure App Service** | Deploy via zip deploy, Web Deploy, or CI; configure scale-out and app settings |
| **Azure Static Web Apps** | For standalone WASM; supports managed Functions API backend |
| **Containers (Docker)** | Preferred for cloud-native; use multi-stage `Dockerfile`; set `ASPNETCORE_URLS` |
| **Azure Container Apps** | Serverless containers; Dapr support; recommended for microservice scenarios |

### Docker / Container Standards
```dockerfile
# Recommended multi-stage Dockerfile for Blazor Web App (.NET 8/10)
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS base
WORKDIR /app
EXPOSE 8080

FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app/publish

FROM base AS final
WORKDIR /app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "MyApp.dll"]
```
- Use official `mcr.microsoft.com/dotnet/aspnet:8.0` or `aspnet:10.0` base images.
- Never run containers as `root`; add `USER app` after `COPY`.
- Set `ASPNETCORE_ENVIRONMENT` via environment variable at runtime.

### Health Checks & Observability
- Register health checks: `builder.Services.AddHealthChecks()` + `.MapHealthChecks("/healthz")`.
- Expose `/healthz/ready` (readiness) and `/healthz/live` (liveness) endpoints for Kubernetes.
- Enable OpenTelemetry (`AddOpenTelemetry`) for distributed tracing and metrics in .NET 8+.
- Use `AddApplicationInsightsTelemetry` or OpenTelemetry OTLP exporter for production monitoring.

### CI/CD Pipeline — Deployment Steps
```yaml
# Required deployment steps
- dotnet restore --locked-mode
- dotnet build -c Release /p:TreatWarningsAsErrors=true
- dotnet test -c Release
- dotnet publish -c Release -o ./publish
- docker build / push  (if containerized)
```
- Use deployment slots (Azure) or canary deployments for zero-downtime releases.
- Run smoke tests against the deployed endpoint before shifting production traffic.

## Measured Standards (Mandatory)

- [ ] `dotnet publish` step documented and reproducible in CI for the target hosting model.
- [ ] No secrets in source; production secrets sourced from Key Vault or CI secret store.
- [ ] Health check endpoints (`/healthz`) present and tested for deployed applications.
- [ ] Containerized apps use multi-stage `Dockerfile`, run as non-root user, and expose only necessary ports.
- [ ] OpenTelemetry or Application Insights configured for production deployments.
- [ ] Environment-specific `appsettings` validated in staging before production promotion.

- [ ] CI deployment workflow snippet covering publish, optional Docker push, and smoke test step.
- [ ] Deployment checklist (environment variables, secrets, health check URLs, rollback procedure).
